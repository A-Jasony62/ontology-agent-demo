## 三条扩展路径

前 7 篇你都在"用"示例本体（智能体任务编排）。这一篇讲"造"：把这套能力变成你自己的。按改动量从小到大，有三条路径：

![把本体服务变成你自己的：三条扩展路径](assets/08-extend.png)

| 路径 | 场景 | 改动量 |
|---|---|---|
| **A 换同构本体** | 业务结构相似，只是类名/属性名不同 | 最小：改配置，不改代码 |
| **B 新建领域** | 完全不同的业务 | 中：拷贝模板，核心零改动 |
| **C 加规则/查询** | 在现有领域上增量扩展 | 小-中：三处联动 |

**共同前提**：核心层（reasoner/）零领域词汇——所以无论怎么扩展，引擎、API、MCP、CLI 都不用改。

## 路径 A：换一个同构本体（实测）

假设你的业务叫"工人-工作"：类叫 Worker/Job/Pipeline，属性叫 owns_skill/needs_skill，但结构（谁有技能、任务要什么技能、复合任务由子任务组成）和示例本体一模一样。

只需要两步配置。在容器内跑（容器已含全部代码与依赖，`-T` 关闭 TTY 以支持管道输入）：

```bash
docker compose exec -T api python - <<'EOF'
from reasoner.engine import OntologyEngine
from domains.agent_task import AgentTaskAdapter, DEFAULT_CONFIG

# 0. 构造最小"工人-工作"同构本体（类/属性名不同，公理结构保留）
owl = '''<?xml version="1.0"?>
<rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#"
         xmlns:owl="http://www.w3.org/2002/07/owl#"
         xmlns="http://demo.example.org/worker-job#">
  <owl:Class rdf:about="http://demo.example.org/worker-job#Worker"/>
  <owl:Class rdf:about="http://demo.example.org/worker-job#Job"/>
  <owl:Class rdf:about="http://demo.example.org/worker-job#Pipeline"/>
  <owl:Class rdf:about="http://demo.example.org/worker-job#Coding"/>
  <owl:ObjectProperty rdf:about="http://demo.example.org/worker-job#owns_skill"/>
  <owl:ObjectProperty rdf:about="http://demo.example.org/worker-job#needs_skill"/>
  <owl:ObjectProperty rdf:about="http://demo.example.org/worker-job#part_of"/>
  <rdf:Description rdf:about="http://demo.example.org/worker-job#worker_a">
    <rdf:type rdf:resource="http://demo.example.org/worker-job#Worker"/>
    <owns_skill rdf:resource="http://demo.example.org/worker-job#Coding"/>
  </rdf:Description>
  <rdf:Description rdf:about="http://demo.example.org/worker-job#job_x">
    <rdf:type rdf:resource="http://demo.example.org/worker-job#Job"/>
    <needs_skill rdf:resource="http://demo.example.org/worker-job#Coding"/>
  </rdf:Description>
  <rdf:Description rdf:about="http://demo.example.org/worker-job#pipe_p">
    <rdf:type rdf:resource="http://demo.example.org/worker-job#Pipeline"/>
    <part_of rdf:resource="http://demo.example.org/worker-job#job_x"/>
  </rdf:Description>
</rdf:RDF>'''
open("/tmp/worker_job.owl", "w").write(owl)

# 1. 加载新本体，必须传命名空间！
eng = OntologyEngine("/tmp/worker_job.owl", ns="http://demo.example.org/worker-job#")

# 2. 覆盖类角色映射，领域查询原样复用
adapter = AgentTaskAdapter(eng, DEFAULT_CONFIG.update(
    agent_class="Worker", task_class="Job", complex_task_class="Pipeline",
    has_capability="owns_skill", requires_capability="needs_skill"))

print("agents():", [a.split('#')[-1] for a in adapter.agents()])
print("tasks():", [t.split('#')[-1] for t in adapter.tasks()])
print("复合任务识别 pipe_p:", adapter.is_complex_task(adapter.NS["pipe_p"]))
EOF
```

**这段 XML 在说什么**（读者第一次"手写"本体，逐块对照）：

| 代码块 | 作用 | 对应知识 |
|---|---|---|
| `<rdf:RDF ... xmlns="http://demo.example.org/worker-job#">` | 文件根 + 命名空间：本文件所有无前缀的名字都归这个 IRI 管 | 篇 1 的 IRI 概念 |
| `<owl:Class rdf:about="...#Worker"/>`（3 行） | 声明 3 个类：Worker、Job、Pipeline；`/>` 是"没有内容"的自闭合标签 | 篇 1 的 `owl:Class` |
| `<owl:ObjectProperty rdf:about="...#owns_skill"/>`（3 行） | 声明 3 个对象属性：owns_skill、needs_skill、part_of | 篇 3 的 `ObjectProperty` |
| `<rdf:Description rdf:about="...#worker_a">` | 声明一个**个体**（这里没有用 owl:NamedIndividual，rdf:Description 是更通用的写法） | 篇 1 的"个体" |
| `<rdf:type rdf:resource="...#Worker"/>` | 声明这个个体**是 Worker 类的一员**（"是一个"） | 篇 1 附录的 `rdf:type` |
| `<owns_skill rdf:resource="...#Coding"/>` | 给个体加一条关系：worker_a 具备 Coding 能力。**不带前缀的属性名**默认属于本文件命名空间 | 篇 1 的三元组 |

整段 XML 产生的关键三元组：`worker_a rdf:type Worker`、`worker_a owns_skill Coding`、`job_x needs_skill Coding`、`pipe_p part_of job_x`——用篇 1 学过的读法，这段就完全可读了。

实测结果（最小同构本体，上脚本容器内输出）：

```text
agents(): ['worker_a']              # Worker 类的个体
tasks():  ['job_x']                 # Job 类的个体
复合任务识别 pipe_p: True           # Pipeline 类被识别为复合任务
classify 新个体 job_y: 正常分类      # 新增/分类能力照常工作
```

**两个关键点（都是实测踩出来的）**：

1. **必须传 `ns` 参数**。引擎的默认命名空间是示例本体的（`agent-task-ontology#`），不传的话，`Worker` 会被解析成示例本体的命名空间下，查不到任何个体——表现为 `agents()` 静默返回空。**换本体第一件事：确认命名空间并传入**。
2. **公理结构必须保留，但 R2/R4 是刻意放进代码的，不是"OWL 表达不了"**。R1 属性链（`has_capability ◦ required_by ⊑ can_execute`）、R3 传递闭包这些推理规则活在**本体公理**里，新本体保留同样结构即可自动复用；R2/R4 在适配器代码里、与本体解耦。这里有个初学者易踩的坑：R2 的组合语义（整体由各部分组成、能做全部部分 ⇒ 能做整体）**OWL 2 本就能表达**——项目之所以用 `_apply_r2()` 在代码里生成它，是为了**不让 .owl 因"每智能体一条组合公理"而膨胀**、保持本体定义文件简洁。这是工程权衡，不是语言限制。换领域时 R2/R4 这类"脚本生成 / 运行时校验"的规则天然不受影响，但**该不该为你的新领域写类似的组合规则，取决于业务是否真的需要这种聚合语义**（见路径 C）。

## 路径 B：新建一个领域（七步）

业务异构时（比如从"任务编排"换到"供应链风险"），新建领域包。按 DESIGN.md 的约定，**新增一个领域 = 在 `domains/` 下新建一个自包含目录，暴露约定符号，引擎/API/MCP/CLI 全部复用，零改动**：

```
domains/<name>/
├── __init__.py            # 纯导出：转发 adapter / mcp 的符号
├── adapter.py             # 业务逻辑（必暴露 NAME/DESCRIPTION/ONTO_FILE/create_adapter）
├── config.json            # 领域语义配置（类角色映射）
├── derivation.json        # 推导链配置（文案 + 展开规则）
├── mcp.py                 # 领域 MCP 工具注册（可选，有则自动加载）
└── <name>_ontology.owl    # 本体定义（Protege 可编辑）
```

七步流程：

1. 建目录 `domains/<name>/`，**拷贝 `agent_task` 作模板**；
2. 替换本体 `.owl`（用 Protege 建模，**中文名统一放 `rdfs:label`**——它是中文名的唯一事实源）；
3. 改 `config.json` 的类角色映射与结构数据；
4. 改 `derivation.json` 的文案与展开规则；
5. 重写 `adapter.py` 的查询方法（引擎原语 + 你的业务规则），暴露 `NAME/DESCRIPTION/ONTO_FILE`；
6. （可选）写 `mcp.py` 注册该领域的 MCP 工具（供智能体调用）；
7. 验证：`list_domains()` 出现新领域 → `load_domain("name", engine)` 能加载 → `mcp/mcp_server.py --domain name` 自动切换领域工具。

注意第 3–4 步和 `adapter.py` 的职责分工：**配置管"语义映射"，代码管"业务逻辑"**。绝大多数"换个说法"（类名、属性名、展示文案）动配置即可。

## 路径 C：加规则与查询类型

在现有领域上增量扩展，两条分支：

**加一条推理规则**

| 规则性质 | 做法 |
|---|---|
| OWL 能表达（属性链/传递/子类） | 加进本体公理，owlrl 自动推理，**零代码** |
| 关系若写成 OWL 公理会让 .owl 随个体膨胀（如 R2 复合委派：OWL 2 能表达，但为保持本体文件简洁改由脚本生成），或本质是运行时校验（如 R4 合规冲突） | 在适配器加方法，并在 `derivation.json` 的 `derivations` 增加对应 key（否则"为什么"缺文案） |

**加一个查询类型**（三处联动）

1. 适配器加方法（返回 dict，可附 `derivation` 推导链）；
2. `derivation.json` 加对应 key（`expand` 按 key 查找展开文案）；
3. 出口注册：API 层加端点，或领域 `mcp.py` 的 `register_tools` 里加 `@server.tool`。

## 一条原则贯穿始终

> **本体管"是什么、能推出什么"，适配器管"业务怎么问"，配置管"说法怎么变"。三者分离，扩展才不用动核心。**

- **本体是唯一事实源**：类/个体/属性/中文名都在 .owl 里，配置不重复维护；
- **配置即行为**：改 `DEFAULT_CONFIG.update(...)` 就换了语义绑定，代码不动；
- **领域包自包含**：一个目录装下一个业务的全部，可插拔、可拷贝、可分享。

## 常见问题

- **Q：换本体后推理规则还能用吗？**
  A：公理结构保留即可——R1 属性链、R3 传递闭包活在公理里，随本体一起换；R2/R4 业务规则在适配器代码里，与本体解耦。所以"同构本体"意味着两者都不用动。
- **Q：不想用 Python 技术栈怎么办？**
  A：本体本身是标准 RDF/OWL 文件，任何支持 OWL 的工具链（Protege、owlready2、任意图数据库）都能消费；本项目只是提供了一套开箱即用的服务层。架构思路（核心零领域词汇 + 领域包可插拔）与语言无关。

## 附录：本文用到的 OWL 语法

本篇是第一次"手写"完整 OWL 文件。`owl:Class`、`owl:ObjectProperty`、`rdf:about/rdf:resource`、`rdfs:label` 等已在篇 1/3 学过（下表标 ★）；以下为本篇新增写法，集中说明：

| 语法 | 作用 | 例子 | 对应的三元组 |
|---|---|---|---|
| `<rdf:RDF ... xmlns="...">` | 文件根 + 默认命名空间：文件里**不带前缀**的名字都归这个 IRI 管 | `xmlns="http://demo.example.org/worker-job#"` | —（文件外壳） |
| `<rdf:Description rdf:about="#x">` | 声明一个个体 x（比 `owl:NamedIndividual` 更通用的写法） | `#worker_a` | `x rdf:type owl:NamedIndividual` |
| `<rdf:type rdf:resource="#C"/>` | 声明"x 是类 C 的一员" | `worker_a → Worker` | `x rdf:type C` |
| 无前缀属性 `<p rdf:resource="#v"/>` | 给 x 加一条关系：x 的 p 属性取值 v（p 属于默认命名空间） | `<owns_skill rdf:resource="#Coding"/>` | `x p v` |
| 自闭合标签 `/>` | 没有内容的标签（只声明、不带属性说明） | `<owl:Class rdf:about="#Worker"/>` | —（写法） |
| `owl:Class` / `owl:ObjectProperty` / `rdfs:label` / `rdf:about` / `rdf:resource` | ★ 篇 1 / 篇 3 已学，此处复习 | | |

> 至此你已读完全系列出现的所有 OWL 语法：声明类、声明属性、限制方向（domain/range）、表达继承、传递、逆属性与属性链，以及声明个体与个体间的关系——**这份速查就是你自己建模时的最小工具箱**。
