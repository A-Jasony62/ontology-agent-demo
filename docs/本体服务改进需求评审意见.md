## 3. 阻断项（必须修订后才能实施）

### BLOCK-1：assign 状态无持久化归属——REQ-02/05 存在覆盖盲区

**现象**：`assign` 产生的分配记录存在**适配器实例的内存 dict**（`adapter.py:63,266` `self.assignments`），
**并没有断言进图**——`graph_export` 中的 `assigned_to` 边是遍历该 dict 生成的（`adapter.py:424-425`）。

**影响**：
- REQ-05 `persist=true` 只覆盖 classify 的图断言（`add_type/add_literal/add_triple`），**assign 状态落不了盘**；
- 即使 REQ-01/06 完成后 reload，assign 状态也**无法从 extensions/ 恢复**（它不是图数据）；
- 现状比说明书 2.2 描述的"双进程互不可见"更严重：**同进程内 reload 都会丢分配**。

**修改建议**（三选一，需明确写入需求）：
1. **assign 改为图断言**（`g.add((task, assigned_to, agent))`）+ 增量落盘（与 classify 同机制）——推荐，符合"单一写入者 + 可持久化"目标；
2. 或明确 assign 为**会话级临时状态**（不跨重启），在 REQ-02 写入者约定中显式声明，并让 `consistency`/`status` 标注其"非持久"属性；
3. 或引入**统一变更日志重放**机制（变更日志除审计外兼作状态恢复源）。

无论选哪个，REQ-03 的"dirty 标记/变更数"都要把 assignments dict 纳入统计，否则状态显示与实际不一致。

## 4. 必改项（修订后应解决）

### MUST-1：REQ-01 MCP 端 SIGHUP 的实现方式需重新定义

**现象**：MCP 工具通过闭包绑定 engine/adapter 对象（`domains/agent_task/mcp.py` 的 `register_tools` 闭包捕获 adapter），
`mcp_server.py:48-63` `build_server` 注册时即固化。

**影响**：SIGHUP 后只"换 engine 引用"无效——工具闭包仍指向旧 adapter 内存对象；旧本体不会生效。

**修改建议**：SIGHUP handler 执行 **完整重建**：`重建 engine（重 parse 核心+extensions）→ load_domain → build_server → 替换运行中的 server`；
或改造工具闭包为**动态查找**（注册时存"取 adapter 的工厂"，调用时才解析当前实例）。需求需写明"重建粒度=server 级"。

### MUST-2：REQ-06 extensions/ 文件格式与加载规范未定义到可实施粒度

**现象**：仅说"`*.ttl | *.owl` 按文件名排序加载"，但未定义：增量文件的命名规范（同日多文件）、
重复个体处理（与核心 .owl 同名个体是覆盖还是冲突）、加载失败语义（单文件坏是否整体失败）、
`raw` 快照与命名空间推导（`engine.py:49-98` `_resolve_ns` 用 `ET.parse(onto_path)` 只读单文件）在多文件下的兼容。

**修改建议**：
- 命名规范：`YYYYMMDD-HHMMSS-<序号>-<用途>.ttl`（排序即时间序）；
- 重复个体：**冲突即拒绝加载**（reload 报错并定位文件），避免静默覆盖核心定义；
- 多文件加载后 `raw` 快照 = 核心+全部扩展的原始断言（物化 diff 才正确）；
- 命名空间推导改为从**已合并图**统计（现有 `_resolve_ns` 已有 IRI 频率分支，去掉文件头依赖即可）。

### MUST-3：并发写保护缺失

**现象**：REQ-02 解决**跨进程**一致性（单一写入者），但**进程内**未定义：FastAPI 多线程下
classify/delete/import 并发写同一 Graph（rdflib 无内置锁）。

**修改建议**：领域写操作（classify/delete/revoke/import）加**进程内互斥锁**（写时串行化 + reparse 串行），
需求中显式声明"单一写入者 = 跨进程唯一入口 + 进程内串行化"两层含义。

### MUST-4：REQ-05 与 REQ-06 强耦合，建议合并为一个 P0 批次

**现象**：`persist=true` 写 extensions/ 依赖 REQ-06 的目录结构；REQ-06 的加载能力依赖 engine 多文件改造。
拆分交付会导致"persist 无落盘目标"或"extensions 无法加载"的半成品。

**修改建议**：REQ-05 + REQ-06 合并为一批（同 PR/同发布），验收标准共享。

### MUST-5：9 项需求均无测试策略

**现象**：现有 pytest 基线（29 项）是唯一的自动验收闸门，但需求清单未要求为 REQ-01~09 增加测试。

**修改建议**：每项需求补充"测试用例要点"（如：reload 损坏文件回退旧状态、persist 后重启恢复、extensions 冲突拒绝、
delete 后推理结论清理、import 事务回滚、并发写串行化），并纳入验收标准。

## 6. 需求遗漏（建议补充）

1. **assign 持久化**（见 BLOCK-1）——最优先；
2. **回滚级联语义**：rollback 删除扩展文件后，assignments dict / r2_asserted 的处理（reload 后 R2 可重跑恢复、assign 恢复不了）——与 BLOCK-1 同源；
3. **extensions 与自动生成的衔接**：REQ-06 的"核心 .owl（build 脚本生成，保持干净）+ extensions/（运行期增量）"正是
   `LLM_WIKI_GENERATION.md` 中"生成器产物（核心定义）与运行时增量（智能体操作）"的分界——建议在需求中显式声明两者关系，
   避免未来生成流程与运行增量互相污染；
4. **变更日志的存储格式**：REQ-03 说"内存+可选落盘"，建议明确落盘格式（JSONL 追加）与轮转策略；
5. **权限/审计**：delete/import/rollback 属破坏性操作，建议记录操作者+时间+前置校验（如：不可删除有依赖关系的个体）。
